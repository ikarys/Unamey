# Agent comparison: bare Opus vs design skill vs Unamey pack

Date: 2026-11-19. Commit: see `git log` for this file. Status: one-shot runs
done on three briefs, correction rounds not yet measured (see "Next").

## Question

The README claims that agent-built screens are clean but visual only, with no
structure tied to the task, and that a pack fixes that before the agent writes a
line. This report checks the claim with the same agent and the same prompt,
three ways:

| Arm | Agent | Design input |
| --- | --- | --- |
| A | Claude Code, Opus (`claude-opus-5-5`), bare config | none |
| B | same | the official `frontend-design` skill, installed in `.claude/skills/` |
| C | same | a Unamey pack for the brief, installed as `.claude/skills/ui-pack/` |

"Bare config" means a fresh `CLAUDE_CONFIG_DIR` holding only the credentials: no
user hooks, no plugins, no global skills, no CLAUDE.md. Arms B and C differ from
A only by the skill directory and one sentence in the prompt naming it.

Two series were run, on two briefs for the same product (a support ticket desk):

- Series 1, `brief.txt`: a detailed brief, the way a developer writes one
  (8 agents; queue sorted by SLA with five fields; selected ticket with
  conversation and customer details; five actions; three queue filters;
  search by customer).
- Series 2, `brief2.txt`: two sentences. "An internal support desk for a B2B
  SaaS company. Eight agents handle customer tickets all day at their desks."
  This is the case the README is about: the agent has to infer the structure.
- Series 3, `brief3.txt`: an unusual domain, three sentences. A seed bank:
  four curators, 3,000 seed lots in freezers, germination tests every few
  years, and the decision of which lots to regenerate in the field before
  they lose viability. No well-known product to replay from memory.

## Protocol

Everything needed to re-run is in `scripts/compare_agents/`:

- `brief.txt`, `brief2.txt`: the briefs above.
- `task.txt`: the task given to the agent (one standalone `screen.html`,
  desktop 1440x900 usable at 1024, Tailwind CDN, inline SVG, realistic data,
  no JavaScript, no shell commands).
- `run_arm.sh <arm-dir> "<extra sentence>"`: runs `claude -p` with
  `--output-format json`, records turns, wall time, API time, cost and tokens
  from the JSON result, and screenshots `screen.html` at 1440x900 with headless
  Chromium. `BRIEF=` selects the brief.

The packs of arm C were generated by Unamey from the same brief with the local
model (`qwen3.8-27b`), one variant, archetype and structure left to the
planner, then exported as the generation's pack (`SKILL.md`, `tokens.css`,
`reference.html`). The `SKILL.md` files and reference pages are in
`agent-comparison/` (`unamey-pack-SKILL.md`, `unamey-reference.png`, and the
`-2` versions for series 2).

Cost of the packs themselves (local model, free for the user, counted here for
honesty):

## Findings

1. **On this brief, bare Opus already gets the structure right.** With the
   detailed brief, all three arms produce a complete master list + detail
   screen that ticks every checklist item. With the two-sentence brief, bare
   Opus still infers a queue sorted by SLA, Mine / Unassigned / All tabs, the
   conversation, a customer panel with plan, ARR and account manager, and the
   reply box. The README's claim that an agent gives "a sidebar, a top bar, KPI
   tiles and a table" does not hold for `claude-opus-5-5` on a support desk.
   No arm produced dashboard filler.
2. **The pack changes the look and the shell, not the structure.** Arm C
   follows the pack's dark tokens, fonts, 4 px radii, icon rail and top bar,
   and the reference's density (17 rows against 9 to 13 elsewhere). The
   structure it follows is the one the agent would have chosen anyway.
3. **The design skill changes the look too, differently.** Arm B is cream and
   teal, arm B2 is light with a dark rail. Both are more distinctive than bare
   Opus's default indigo on slate, and the skill cost one or two extra turns.
4. **The pack costs more at generation time, not less.** Arm C used the most
   turns and tokens of series 1 (reading `SKILL.md` and `reference.html`), plus
   the pack's own generation. The expected saving, fewer correction rounds, is
   not visible in a one-shot run because there was nothing to correct.
5. **What the pack does provide that the others do not**: a design decided
   and viewable before the agent starts, a reference page the agent copies
   instead of inventing, and the same shell and tokens for every later screen.
   Whether that saves correction rounds on the second and third screens of a
   project is the open question, not answered here.
6. **Unamey's own reference pages are weaker than the agent's screens.** The
   local model's reference for series 2 has a wrapping ticket id and an empty
   lower half. The pack is a brief for the agent, not a finished screen, but a
   reader comparing `unamey-reference-2.png` with `A2-bare.png` would pick A2.
   The series 3 reference truncates every lot id and shows 8 rows.
7. **The unusual domain did not change the picture.** On the seed bank, all
   three arms produced a task-specific screen with a ranked list, the
   regeneration standard, a germination history chart and a regeneration
   action; none produced a generic dashboard. The best framing of the
   decision came from the design skill (arm B3: lots crossing the standard
   per year against field capacity, with batch "add to field plan"), not from
   the pack. The pack arm (C3) is the densest and most complete triage view
   but is the only one without the field-capacity constraint, because the
   pack's reference does not have it. Unamey's planner chose "Dense operator
   console, master list + detail" for all three briefs; the structure choice
   the README advertises was not exercised. Arm C3 was the cheapest of its
   series (fewest output tokens: the agent copied the reference instead of
   inventing), a first sign of the expected saving, on one run.
8. **With a stronger model behind Unamey, the pack does drive the structure.**
   The DeepSeek planner chose "Analytics board, Dashboard" for the seed bank
   and justified it (the curators' first job is monitoring viability, not
   editing a grid), where qwen had chosen master list + detail three times. Its
   reference has the freezer and field-plot capacity that the qwen reference
   lacked, no truncated ids and no empty area. Arm C3d reproduced that
   reference closely: Opus kept the dashboard structure, the two-row top bar,
   the KPI band, the two charts and the capacity panels, and extended it with a
   ranked regeneration queue with row actions. So finding 2 was an artefact of
   the pack and the agent agreeing: when the pack's structure differs from
   what Opus would pick, Opus follows the pack. Whether that structure is the
   right one is a separate question: for the brief's decision (which lots to
   regenerate), the per-lot history and the ranked queue of A3, B3 and C3 are
   closer to the task than a monitoring dashboard whose queue sits below the
   fold. The cost saving of C3 disappeared (C3d cost as much as A3), and the
   pack took 206 s and 44 k output tokens to generate, at $0 on this endpoint.

Conclusion for the README: the positioning "agents give generic, visual-only
screens" is not supported by this test for the current Opus, on a common
product or on an unusual one. The claim should
be narrowed to what was observed: a pack fixes look, shell and density before
the agent starts and keeps them across screens. The correction-rounds saving
stays a hypothesis until measured on a multi-screen project. The pack's
quality, and with it the structure the agent ends up with, depends on the
model behind Unamey: the same pipeline gave a dashboard with capacity panels
on DeepSeek and a truncated master-detail on the local qwen.

## Limits

- Two products, three briefs, one run per arm, one judge. The seed bank is
  unusual but still a list-of-things-to-triage shape; a board or scheduling
  shape is untested.
- The packs were built for these very briefs, so arm C partly translates a
  finished design. That is the product's point, but it is why the pack's own
  cost is listed above.
- The checklist is a proxy for correction prompts. The real measurement, the
  rounds and tokens needed to reach an accepted screen, is the next step.
- The agent's screens were judged on one screenshot each; nothing says the
  HTML is well structured for a developer to continue from.

## Next

- Multi-screen run: ask each arm for three screens of the same product (queue,
  customer page, reports) and count the correction prompts needed to make them
  consistent. This is where a pack should show a difference.
- A brief whose right structure is not a list + detail (a scheduling grid, a
  board, a step flow), to test the planner's structure choice.
- The planner's fixed choice came at least partly from the model: the same
  brief and pipeline gave a different, justified structure on DeepSeek. Still
  to check whether the brief helper's style tags bias the local model.
- Judge the structure choice itself: the DeepSeek pack picked a dashboard for
  a decision task; a planner rubric ("what does the user decide on this
  screen?") may be needed before the archetype step.
- Correction rounds on the checklist misses of series 2 (merge, assign,
  priority), one prompt per round, recording rounds, tokens and cost per arm.
