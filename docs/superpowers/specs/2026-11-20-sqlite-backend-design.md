# SQLite backend for local development

Date: 2026-11-20. Status: draft for review.

## Goal

Run `studio` without Docker for local development and tests: SQLite in a
local file when `DATABASE_URL` is not set, PostgreSQL when it points at one.
Both backends are supported in the same binary; the backend is chosen at
runtime from the URL scheme. MySQL is out of scope (decided 2026-11-20).

## Decisions already taken with the maintainer

- SQLite + PostgreSQL, not MySQL.
- Backend selected at runtime by the `DATABASE_URL` scheme, through an enum
  wrapping the two rango pools. No `DATABASE_URL`: SQLite in a local file.
- The Help page shipped first; this is the next piece of work.

## Current state (what the change has to touch)

- `src/config.rs` holds a `rango::PgPool`; `src/pg.rs` connects and builds
  test databases by cloning `studio_test` on the dev Postgres.
- `src/db.rs` (2131 lines) runs 86 raw `sqlx::query` calls, plus a handful
  in `cache.rs`, `jobs.rs`, `pipeline/generate.rs`, `pipeline/pack.rs` and
  the `http.rs` tests. rango ops (`insert`, `get`, `update`) cover
  single-row work. Twelve queries use JOINs and three GROUP BY: rango's
  query builder cannot express them, so a rewrite "on the query builder"
  would mean N+1 queries or raw SQL anyway.
- Postgres-only fragments: `now()` (24), JSON operators `->>` / `#>>` /
  `jsonb_set` / `to_jsonb` / `json_build_object` (10), `date_trunc` (4),
  `interval` (3), `::text` and `::jsonb` casts (8), `ILIKE` (1),
  `sqlx::postgres::PgRow` in `job_json`, `sqlx::PgExecutor` in two helpers,
  `sqlx::query_as` tuples (3), `sqlx::query_scalar` (6), 8 transactions.
- Migrations are generated by the rango CLI (`rango.toml` names ONE
  backend) and applied by `rango migrate`; the binary never applies them.
  rango maps `FieldUuid`, `FieldDateTime` and `FieldJson` to `TEXT` on
  SQLite (UUID string, RFC 3339, serialised JSON) and `FieldBool` to
  `INTEGER`.
- `docs/roadmap.md` records the move from rusqlite to Postgres; this change
  does not bring rusqlite back: SQLite goes through sqlx, like Postgres.

## Design

### 1. One pool enum, one small SQL layer (`src/sql.rs`, replaces `src/pg.rs`)

```rust
pub enum Db { Pg(rango::PgPool), Sqlite(rango::SqlitePool) }
pub enum Tx { Pg(sqlx::Transaction<'static, Postgres>), Sqlite(sqlx::Transaction<'static, Sqlite>) }
pub enum Row { Pg(PgRow), Sqlite(SqliteRow) }
```

- `Db::connect(url)` picks the arm from the scheme (`rango::DatabaseConfig::backend()`),
  `sqlite:` URLs go through `rango::connect_sqlite` (WAL, foreign keys,
  busy timeout), anything else through `rango::connect_postgres`. An
  unknown scheme is an error at startup.
- `Db` and `Tx` expose the same four calls: `fetch_all`, `fetch_optional`,
  `fetch_one`, `execute`, each taking `(sql: &str, args: &[SqlValue])`.
  `Db::begin()` returns a `Tx`; `Tx::commit()`. Internally one generic
  function per backend binds the `rango::SqlValue` list the way rango does
  (SQLite: UUID as text, datetime as RFC 3339, JSON as text, bool as
  integer), so rows written by rango and by raw SQL agree.
- `Row::get::<T>(name)` for the types the code reads today: `Uuid`,
  `String`, `bool`, `i64`, `f64`, `DateTime<Utc>`, `serde_json::Value`
  and their `Option`s. A private trait does the per-backend decoding
  (SQLite parses the text forms). `job_json` and the three `query_as`
  tuples read through it.
- rango model ops used by the code (`insert`, `get`, `update`, `delete`)
  get one-line dispatching wrappers on `Db` and `Tx`, so callers never
  name a backend. rango's two `RangoFilterExt` traits are never both in
  scope (the Postgres one shadows the SQLite one in the prelude): the code
  imports only what the wrapper needs.
- `Config.pool` keeps its name and becomes a `Db`.

### 2. Portable SQL rules (applied to every raw query)

- Placeholders stay `$1`, `$2`, ... in order of first use; SQLite accepts
  `$n` names and binds positionally, so an argument used twice still binds
  once, exactly as in Postgres. Never use `$2` before `$1`.
- No `now()` in SQL: the Rust side binds `Utc::now()` (or the month start,
  or `now - 24h`) as an argument. Removes `now()`, `date_trunc` and
  `interval` in one move and makes those queries testable at a fixed time.
- JSON reads go through one helper, `json_text(col, &["direction","label"])`,
  that renders `col #>> '{direction,label}'` on Postgres and
  `json_extract(col, '$.direction.label')` on SQLite. Column and path are
  `&'static str` literals, never input. `jsonb_array_length`, the `seed`
  cast, `json_build_object` and the `jsonb_set` write in `join_batch`
  become Rust on the whole `notes_json` value (read, modify, update in the
  existing transaction).
- `ILIKE` becomes `lower(col) LIKE lower($1)`; `x::text` becomes
  `CAST(x AS TEXT)`; `right(x, 8)` becomes `substr(x, length(x) - 7)`;
  `ON CONFLICT ... DO UPDATE` and `RETURNING` stay (SQLite >= 3.35, which
  sqlx bundles).
- `COUNT(*)`, JOINs, GROUP BY, `COALESCE`, `CASE`, `EXISTS`, `IN (...)`
  are standard and stay as they are.
- The two helpers taking `impl PgExecutor` take `&mut Tx` (login opens a
  short transaction like signup already does).

### 3. Migrations

- `migrations/` stays the Postgres set, generated and applied as today.
- `migrations/sqlite/` holds the SQLite set with its own `snapshot.json`
  and a two-line `rango.toml` (`backend = "sqlite"`, models path), so
  `just makemigrations-sqlite` runs `rango makemigrations --output .`
  from that directory. Hand-written parts carried over: the local user
  seed (`INSERT OR IGNORE`). The Postgres data moves of 0003 and 0006
  have no SQLite equivalent (no pre-existing SQLite data).
- On SQLite the binary applies pending migrations at startup, embedded
  with `include_str!` and recorded in the same `_rango_migrations` table
  the rango CLI uses (name, applied_at), one transaction per file. So a
  developer needs no CLI and `rango migrate` still works on the same file.
  Postgres keeps the explicit `rango migrate` step: deployments rely on it.
- A test asserts that both migration sets describe the same tables and
  columns (compare the two `snapshot.json` files), so a model change
  cannot land with only one set regenerated.

### 4. Tests

- `test_db()` replaces `pg::test_pool()`: with `TEST_DATABASE_URL` set it
  clones `studio_test` on Postgres as today; without it, a fresh SQLite
  file in the system temp dir, migrated by the embedded applier, deleted
  by a drop guard at the end of the test. Shared-cache in-memory databases
  are avoided: they serialise tables and break concurrent requests in the
  HTTP tests.
- `cargo test` alone runs on SQLite, no Docker. `just test` runs the Rust
  suite on both backends (SQLite, then Postgres), then `tsc` and the
  iframe check. The DB tests are the same 93 tests, parameterised by the
  pool, so every raw query is exercised on both dialects.

### 5. Dev flow and configuration

- `DATABASE_URL` unset: `sqlite://studio.db` next to the binary (created
  on first start, mode 0600 on Unix: it holds password hashes, session
  token hashes and the sealed provider keys). `just dev` uses `dev.db`,
  already git-ignored. `just dev-pg` keeps the Postgres dev flow and the
  existing dev data (`studio` database); `just multi-user` stays on the
  default.
- README (Requirements, Run, variable table), `docs/index.html` (the
  "Docker" requirement line), `docs/architecture.md`, `CONTRIBUTING.md`,
  `VERIFICATION.md` (what `just test` proves on which backend),
  `SECURITY.md` (the spliced JSON paths are literals; the SQLite file
  mode), `docs/roadmap.md` and `AGENTS.md` (`just test` description) are
  updated in the same change.

### 6. Security

- Same claim as today: every value is bound, never spliced. New spliced
  pieces are the JSON column and path literals in `json_text` and the
  existing checked table name; both are `&'static str`.
- SQLite file created 0600; WAL side files inherit the directory's mode,
  documented.
- SQLite enforces the same CHECK, UNIQUE and FOREIGN KEY constraints
  (rango enables `foreign_keys`); the existing tests on refused rows run
  on both backends.

## Out of scope

- MySQL/MariaDB.
- Splitting `db.rs` by domain: a separate change.
- Applying Postgres migrations from the binary.
- Importing existing Postgres dev data into SQLite.

## Verification

- `just test` green on both backends, `cargo clippy -- -D warnings`,
  `cargo fmt --check`, `gitleaks git`.
- Manual: `DATABASE_URL= cargo run -- serve` starts with no Docker, the
  first run creates `studio.db` (mode 0600) and the app works end to end
  (provider, generation, pack); `just dev-pg` still works on Postgres.
